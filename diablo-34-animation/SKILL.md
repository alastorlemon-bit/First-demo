# Анимация в перспективе 3/4: Diablo-like 2.5D

**Лицензия:** MIT.  
**Редакция:** 0.3.4 (03.11.2026); исходная документация v0.2.0 сохранена, дополнена результатами практического полигона.

> **ВАЖНО:** это скилл о **наклонной плоскости земли и согласовании движения/анимации с камерой**, а не о привычном виде персонажа «в три четверти» при боковой прокрутке. Применять при создании или исправлении 2D/2.5D игр с фиксированной камерой сверху под углом: diabloid, изометрия, псевдоизометрия, косоугольная проекция.

## Принцип

Точка контакта персонажа с землёй живёт в координатах мира. Её проекция на экран определяет положение персонажа, тени, сортировку по глубине и основу контакта ног. Спрайт/риг — **изображение поверх точки опоры**, а не источник координат мира. Все движения тела должны уважать общую проекцию камеры.

## Сначала определить тип камеры

- **Изометрическая / аксонометрическая**: постоянный масштаб, параллельные линии; допустима линейная проекция через два базисных вектора.
- **Псевдоизометрическая 3/4**: углы и сжатие глубины могут отличаться от строгой изометрии; восстановить базис по референсу и зафиксировать его в настройках камеры.
- **Настоящая перспективная камера**: есть сходящиеся линии и изменение масштаба с удалением. Не подменять её линейной формулой; использовать матрицу проекции/проецирование луча на плоскость и модель масштаба по глубине.

Если тип камеры или наклон не очевиден, измерить направления двух независимых осей земли по референсу, сопоставить размер одинаковых объектов на ближнем и дальнем плане. Не задавать угол 45° и 2:1 «по умолчанию» просто потому, что сцена похожа на изометрию.

## Математическая модель для фиксированной аксонометрии

Мир: `p=(x, y)` — точка на земле, `z` — высота над землёй, `origin=(ox, oy)` — экранное начало координат.

```js
// Два экранных вектора единичного смещения по осям земли.
const camera = {
  ox: 0, oy: 0,
  ux: 32, uy: 16,    // ось x мира
  vx: -32, vy: 16,   // ось y мира
  heightPx: 48       // пикселей на единицу z
};

function projectGround(x, y, c = camera) {
  return {
    x: c.ox + c.ux * x + c.vx * y,
    y: c.oy + c.uy * x + c.vy * y
  };
}

function projectActor(x, y, z, c = camera) {
  const foot = projectGround(x, y, c);
  return { x: foot.x, y: foot.y - z * c.heightPx };
}
```

Это **пример строгой 2:1 изометрии**, а не обязательные числа. Для конкретного проекта брать коэффициенты из существующей камеры или калибровать их по графическому референсу. Все объекты используют одну и ту же проекцию.

## Контракт персонажа и ассетов

Для каждого актёра хранить отдельно:

1. `worldPosition`: позиция точки опоры на земле `(x,y)`, отдельно `height/z`.
2. `groundAnchor`: пиксельный якорь в контакте стоп с землёй; **не** центр картинки или прямоугольник коллизии.
3. `footprint`: логическая зона столкновения на земле (обычно эллипс или небольшой многоугольник).
4. `facing`: направление в мире / один из 8 экранных ракурсов; позы соответствуют ему.
5. `animationState`: idle, start, walk, run, stop, jump, fall, land, attack и т. д.
6. `shadow`: отдельный слой на плоскости под персонажем, привязанный к `worldPosition`.

Заложить 8 направлений: N, NE, E, SE, S, SW, W, NW (можно 4, если стиль проекта это допускает). При асимметрии оружия, одежды, волос, рюкзака или рук **не зеркалить слепо**: отмечать, какой предмет в какой анатомической руке, и готовить отдельные ракурсы, если зеркалирование изменяет смысл.

## Как анимировать движение по земле

1. Считать **скорость в координатах мира**, нормализуя ввод по диагонали, чтобы диагональное движение не ускоряло персонажа.
2. Проецировать реальное перемещение в экранные координаты; выбирать ракурс из направления **проецированной скорости** согласно принятой схеме спрайтов.
3. Хранить циклы шага с чередованием **анатомически левой/правой** ноги. Во время опорной фазы фиксировать стопу на соответствующей точке земли; при переносе двигать её по дуге.
4. Для рига делать IK ног только с зафиксированными опорными целями. Если риг не обеспечивает силуэт, использовать рисованные ключевые позы, а риг — только для вторичных движений.
5. Отдельно управлять bob тела, наклоном, одеждой и тенями; ни один из них не должен незаметно перемещать точку опоры персонажа.
6. При старте, остановке и смене направления сохранять последовательность ног и контакт стоп; переход между ракурсами не должен менять мировую позицию или телепортировать конечности.

## Глубина, высота, прыжок, препятствия

- **Depth sorting:** первичный ключ — проецированная экранная `y` **точки контакта с землёй**. В статических объектах заранее различать заднюю и переднюю части (например, за стволом можно скрыться, под кроной можно пройти). Для пересекающихся больших объектов использовать дополнительные слои/окклюзионные маски.
- **Прыжок:** координата земли движется в `(x,y)`, высота `z` меняет экранную позицию видимого персонажа. Тень остаётся на земле под ним, может меняться по размеру/прозрачности. Столкновения на земле и приземление считаются по мировым координатам, не по верхнему краю спрайта.
- **Склоны и лестницы:** хранить высоту поверхности `groundHeight(x,y)` и проверять опору на этой высоте. Не изображать подъём простым сдвигом картинки без обновления физики.
- **Перекрытия:** герой проходит перед ближними объектами и за дальними; тестировать на диагональных траекториях, а не только слева направо.

## Процесс работы с референсом

1. Проверить **существующий проект** и его камеру, координаты, спрайты, масштаб; не заменять движок без запроса.
2. Определить/измерить проекцию плоскости и отметить линии её двух осей поверх референса.
3. На одном тестовом объекте проверить точку опоры, позицию и сортировку по глубине.
4. Сделать 8 направлений движения **без анимации** — сначала геометрия и скорость, затем графика.
5. Добавить ключевые позы и цикл ходьбы, после — IK и вторичные движения (по необходимости).
6. Проверить прыжок, тени, перекрытия, смену направления и поведение около препятствий.
7. Внести только локальные изменения; при появлении ошибки сначала сверить проекцию/якорь и систему координат, прежде чем перерисовывать персонажа.

## Проверки качества — обязательные

| Сценарий | Что должно оставаться истинным |
| --- | --- |
| Идём вдоль двух осей земли | Угол и длина смещения соответствуют камере |
| Идём по диагонали | Та же скорость **в мире**, что и прямо |
| Переключаем 8 направлений | Левое/правое не путается, ноги и предметы не «перепрыгивают» |
| Шагаем на месте / движемся | Опорная стопа не скользит относительно земли |
| Проходим перед/за столбом | Перекрытие по глубине без внезапных скачков |
| Подпрыгиваем на месте | Тень остаётся у земной опоры, высота независима от глубины |
| Персонаж идёт по диагонали за стеной | Коллизия считается по footprint, маска перекрытия — по геометрии стены |
| Переходим walk → stop → walk | Нет срывов анимации, совпадает фаза контакта ног |

## Воспроизводимый пайплайн: раскадровка Studio Igor (7–21 минутные фрагменты)

Ниже связаны **пояснения автора и последовательные скриншоты пользователя** из «2D-графика кодом — реально? Делаем 5 игр с Claude и GPT» (Studio Igor, октябрь 2026, фрагмент около 18:50–21:20). Это **разбор демонстрации, а не подтверждение эффективности методом измерений**. Применять при создании нового модуля, не подменять существующую камеру и не переделывать готовые спрайты без запроса.

### A. Графическая база, затем слои сцены

1. Создать **style bible**: указать конкретный наклон камеры (у автора в примере «isometric 2:1 view, 3/4 from above»), палитру, свет, степень детализации и форму контуров. Не считать 2:1 обязательным стандартом; измерять ракурс каждого проекта.
2. Генерировать **один объект на запрос**: исходный герой в референсной позе, конь, повозка, бесшовный грунт. Общий стиль сохранять одним и тем же набором требований. Человеческий персонаж/животное — изначально с удобным для последующей разборки силуэтом и видимыми суставами.
3. Сцену собирать из отдельных слоёв **дальний план / зона лагеря / ближний план** и объектов. На скриншоте они показаны как z0/z1/z2, но **эти три декоративных слоя не заменяют сортировку каждого подвижного объекта по экранной глубине опоры** и не равны физической высоте `z`.
4. PNG хранит **краску**, программный движок добавляет освещение, туман, частицы, воду, масштаб и движение. На кадрах автор прямо противопоставляет «Генератор — Картинка» и «Движок — Код». Сохранять исходные изображения отдельно от эффектов.

### B. Из изображения — управляемый 2D cutout rig

1. Выделить корень тела/таз и скелет: плечи → локти → кисти, бедра → колени → голеностопы/стопы; пометить **анатомически левую и правую** сторону. На кадре «РИГ-ПОЗА» коленные и ножные ориентиры расположены ниже тазовых точек; не переносить бездумно координаты из другого ракурса.
2. Разделять визуальный контур и кости: корпус, голова, плечи, предплечья, бёдра, голени, обувь. Суставы нужно совмещать с арт-формой, а не просто ставить в середину прямоугольников.
3. Если разрез голени/предплечья даёт дырку, добавить **шапку сустава** — круглый или нарисованный перекрывающий фрагмент в цвет соседних частей. На скриншотах: сначала отмечен «ШОВ — СТЫК ДВУХ КУСКОВ», затем «ШАПКА СУСТАВА». Радиус ориентировать на реальную толщину конечности, **не использовать его как универсальное число**. Тестировать при полном рабочем диапазоне сгиба и меняющемся слое перекрытия.
4. Фраза автора «одна нарисованная нога работает за две» описывает **упрощение его демонстрации**, не требование для качественного персонажа. Для главного героя использовать отдельно ближнюю и дальнюю конечности либо проверенные корректирующие варианты. Копирование одного ассета допустимо лишь когда совпадают силуэт, свет и глубинное перекрытие.
5. Для каждого направления зафиксировать pivot частей, исходную ориентацию, порядок слоёв у ближней и дальней стороны. При больших разворотах 3/4 нужен отдельный набор ассетов или корректирующие ключевые формы: простой поворот плоского PNG не восстанавливает скрытую поверхность.

### C. Алгоритм одного шага — зависимая цепочка

Следующая последовательность повторяет **пять подпунктов, показанных автором**: `путь стопы → опора / скорость тела → перенос по дуге → колено через IK → таз по опорной ноге`.

1. **Путь стопы:** определить фазу цикла, цель на земле в мировых координатах и длительность контакта. Использовать независимые индексы для **левой/правой анатомической** ноги со сдвигом фаз примерно 1/2 цикла.
2. **Опора ↔ скорость тела:** в фазе stance сохранить положение контактной стопы **в мире**; персонаж продвигается мимо неё. Нельзя привязать опорную стопу к экранным пикселям, иначе при прокрутке камеры будет скольжение.
3. **Перенос — дуга:** при swing вести свободную стопу к следующей мировой цели; вертикальную высоту подъёма стопы накладывать поверх проекции её пути, не менять геометрию земли.
4. **Колено — IK:** при заданных длинах бедра/голени находить сгиб, сохранять предпочтительную сторону колена и не допускать невозможной длины; при невозможной цели корректировать шаг или позу, не растягивать кость молча.
5. **Таз ← опорная нога:** высота и отклонение таза ограничиваются опорной геометрией; скриншот показывает график «высота таза» с мягкими просадками. Не копировать ритм в пикселях: амплитуду калибровать относительно размера персонажа.
6. **Руки:** балансировать ходьбу противоположным махом рук, но независимо контролировать ближнюю/дальнюю, скрытие за торсом и сгиб локтя. Дальняя конечность не должна «проходить сквозь» грудь.
7. **Направления:** при ходьбе на NE/NW/SE/SW считать движения в координатах земли и только потом проецировать. Спрайтовые клипы `SW`, `NE` на кадрах — разные направления; 16 кадров на цикл — **частный пример QA автора**, не обязательный FPS или размер цикла.

**Минимальный контракт фаз** (условный псевдокод, адаптировать к проекту):

```js
const phase = (time * cadence + legOffset) % 1;  // offset: left 0, right .5
if (phase < stanceFraction) {
  footWorld = lockedContactWorld;                 // контакт не двигается в мире
  footHeight = 0;
} else {
  const u = (phase - stanceFraction) / (1 - stanceFraction);
  footWorld = lerp(previousContactWorld, nextContactWorld, u);
  footHeight = liftHeight * Math.sin(Math.PI * u);
}
const footOnScreen = projectActor(footWorld.x, footWorld.y, footHeight);
// IK + таз → после расчёта опоры, а не до него.
```

`lockedContactWorld`, `previousContactWorld` и `nextContactWorld` обновляются **в момент постановки стопы**, не пересоздаются каждый кадр. Это критично для устранения foot slide.

### D. Мягкая деформация (soft bones) — отдельный тип движения

На скриншотах с лошадью видны **зоны влияния** на шее/голове и хвосте, локальные корни и формула шейдерной деформации в зависимости от веса. Это относится к изгибу **внутри текстуры**, а не к обычному повороту двух жёстких кусков.

- Для шеи животного, волос, хвоста, ремней/плаща задать локальный корень, область влияния и плавное весовое поле: у неподвижного корня вес близок к 0, у подвижной области больше.
- Деформировать пиксели ограниченно относительно соответствующего pivot, проверять контур, растяжение рисунка и сохранение объёма. Шовные маски и soft bones — **разные** техники.
- Не применять такой изгиб ко всему человеку без контроля анатомии; голову, таз и крупные звенья лучше держать жёсткими или использовать корректирующие рисунки.

### E. Проверка перед приёмкой — не только «красиво выглядит»

На финальных кадрах показан экран QA с **четырьмя именованными тестами**: `FOOT SLIDE`, `LIMP`, `STRETCH`, `POP`. Реализовать их сначала хотя бы как измерения/запись и визуальную проверку. Само наличие графика в ролике **не доказывает**, что тест автоматически отбрасывает брак или что анимация идеальна.

| Тест | Что измеряем | Когда провал |
| --- | --- | --- |
| FOOT SLIDE / проскальзывание | разница мировых координат опорной стопы между соседними кадрами | стопа уезжает в течение контакта |
| LIMP / хромота | асимметрия времени контакта, длины шага и вертикального ритма | без причины выраженно различаются левая и правая фазы |
| STRETCH / растяжение костей | длина бедра, голени, плеча и предплечья относительно исходной | звено растянулось без разрешённой деформации |
| POP / рывок | скачок положения/угла сустава и порядка перекрытия на соседних кадрах | видимый мгновенный срыв при переходах или смене направления |

Собрать короткую **контрольную полосу**: idle → первый шаг → цикл на месте → ходьба по диагонали → смена направления → остановка. Смотреть каждый ракурс в полном масштабе и в реальном размере на телефоне. Отдельно проверить визуальные риски, которые QA автора прямо не перечисляет: **ближняя/дальняя рука и нога, силуэт, ступни под тазом, слои при поворотах, совпадение тени и groundAnchor**.

### Что подтверждено источником и что добавлено как наша инженерная корректировка

- **На кадрах/в пояснениях:** style bible; генерация героя, лошади, повозки и земли отдельными запросами; три плана сцены; отдельный PNG и эффекты движка; 2D-кости; шапка сустава; пять шагов алгоритма походки; 16 кадров в примере; soft bones шеи/хвоста лошади; четыре проверки рига.
- **Наши практические дополнения:** привязка опорной стопы к *мировым* координатам, уникальная анатомическая маркировка сторон, корректирующие формы для дальних конечностей, объективные критерии QA и совмещение с существующей проекцией камеры. Это рекомендации, **не утверждения, что автор реализовал всё именно так**.
- **Что не удаётся установить по скриншотам:** точную формулу IK, реальный формат хранения графических сегментов, конкретные пороги тестов, качество переходов в движении и точность реальной анимации при разных ракурсах. Не выдавать их за подтверждённые факты.


## Проверенная механика походки — v0.3.4 (CMU, 2026-11-03)

**Статус:** визуально принята пользователем и проверена на двух диагональных направлениях SW/NE. Это эталон **конкретного полигона**, а не универсальная готовая походка для всех масштабов, скелетов и направлений.

- Полигон: https://alastorlemon-bit.github.io/First-demo/diablo-34/
- Код: https://github.com/alastorlemon-bit/First-demo/blob/main/diablo-34/index.html
- Фиксация: коммит `6c1b19fffba3324fdeaaf2fe26eeacbc562b2f31`.
- Исходный захват движения: Carnegie Mellon mocap `008/08_01.bvh`, 120 Гц, период 121 кадр; для веб-полигона нормализовано 64 выборки. Подтверждённость относится к итоговому ретаргетингу и отображению, а не к точности реконструкции полной исходной записи.

### Что оказалось критичным на реальном тесте

1. **Таз и перенос веса.** В режиме CMU брать высоту таза из траектории `mocapPose(phase)`, сохраняя мягкую латеральную передачу нагрузки и компенсацию плеч/головы. **Не ограничивать высоту таза свободной (swing) стопой:** это давало резкую просадку/подскок в частности при левой опоре. Геометрические ограничения опоры оставить для классической походки, Т-позы и разворота; не применять слепо к мокап-режиму.
2. **Длина шага и анатомия.** Ретаргетировать продольный ход ног под существующие фиксированные длины костей, не вытягивать звенья IK. В принятой модели использовано `retarget = 0.85` от захваченного шага; это **калибровка данной модели**, не универсальный коэффициент. Следить, чтобы цель стопы оставалась достижимой при крайних фазах.
3. **Стопа в мировой опоре.** После контакта сохранять `lockedContactWorld`; не пересчитывать его от экранного таза каждый кадр. Продвижение тела за цикл должно быть согласовано с длиной шага и частотой цикла (`скорость / cadence`), иначе появляется накопленный боковой/продольный дрейф даже при `FOOT SLIDE = 0` в кратком тесте.
4. **Плоская подошва и перекат.** Односоставную жёсткую стопу допустимо рисовать как отрезок `heel → toe` постоянной длины. Во время средней опоры стопа плоская на плоскости земли; ближе к отталкиванию пятка поднимается **поворотом вокруг зафиксированного носка**. В начале переноса угловое положение мягко возвращается. В принятом полигоне длина подошвы `0.38`, максимальный pitch около `0.20` рад; это пример, масштабировать под рисунок. Не требуется добавлять ещё одну кость пальцев только ради переката.
5. **Переходы SW ↔ NE.** При смене направления сохранять текущие мировые положения стоп и их анатомические идентификаторы; в переходной фазе последовательно переставить ноги и лишь затем возобновить ходьбу в новом направлении. Не разворачивать мгновенно экранные координаты опорных стоп.
6. **Колено и общий силуэт.** IK на обеих ногах сохраняет длины звеньев и предпочтительную сторону сгиба. Мокап-ориентир колена можно использовать для направления изгиба; следить за ближней/дальней ногой и не отражать анатомические стороны вместе с направлением камеры.

### Контроль качества перед дальнейшими изменениями

Обязательный короткий прогон для **двух** направлений: старт → несколько циклов → левая опора → правая опора → остановка → разворот → несколько циклов назад. Проверять также по кадрам. Встроенный QA эталонного полигона прошёл **9/9**:

- Отсутствие резкой просадки таза и адекватный перенос веса.
- Плоская опора и перекат без изменения длины подошвы.
- Развороты SW→NE и NE→SW.
- Контакты стоп, сохранение старого режима.
- 20-секундные прогоны SW/NE без накопленного бокового дрейфа.

В проверенных режимах `FOOT SLIDE = 0`, `STRETCH = 0`; контроль `POP` не обнаружил критических скачков (в тестах ниже 8 px). Значения относятся к тестовому полотну и расчётам полигона, их нельзя автоматически считать порогами для другой сцены. На телефоне обязателен **визуальный** контроль: метрики не доказывают естественность силуэта.

### Граница подтверждённого

На момент v0.3.4 подтверждены только SW/NE и схематичный скелет с жёсткой подошвой. **Не подтверждены:** остальные шесть ракурсов, генерация/разрезание графики, швы реальных PNG-частей, оружие/рюкзак, прыжок, лестницы, сложные окклюзии. Новые задачи проверять отдельно и не менять принятую механику без воспроизведённой причины. Правила создания мастер-референса и нарезки графики выносить в отдельный навык `diablo-34-character`; сначала добиться верной анатомии, перспективы и согласованных ракурсов цельного персонажа, потом разрезать.


## Как отвечать при использовании скилла

Перед генерацией ассетов/кода коротко зафиксировать: тип камеры, оси земли, положение groundAnchor, число направлений, формат анимации (покадровая / rig / гибрид). Если данных недостаточно, явно обозначить допущения. Отдавать конкретные исправления в существующий проект и перечислять визуальные тесты. **Не путать перспективу игрового поля 3/4 с «поворотом персонажа в 3/4» для бокового платформера.**

## Практическое дополнение — 04.11.2026: утверждённый манекен и четыре направления

**Текущий источник истины:** `main:diablo-34/HANDOFF_2026-11-04.md` и `main:diablo-34/mannequin-rear-lab.html`. Старые примеры/ограничения в этом скилле, где упомянуты только SW/NE, относились к раннему прототипу; теперь практический полигон поддерживает 4 направления. **Не путать приёмку манекена с испытанием нового персонажа.**

- **SW ↙** — готовый передний атлас; **NE ↗** — готовый задний; **SE ↘** и **NW ↖** — зеркальные соответственно. Перемещение в игре идёт по двум мировым осям; для зеркала проверять анатомические Л/П, цвета, точки и порядок отрисовки, не только подписи.
- Разворот **фас ↔ спина** пользователь утвердил как **немедленную смену готовой позы/атласа**. Попытки размытия, перекрёстной прозрачности, морфинга и визуального сужения персонажа отклонены. Не возвращать их без прямого запроса.
- CMU-запись, фазы шага, опора стоп, IK и мировые длины костей — независимы от спрайтов. Перспективная корректировка **экранных** коленей/запястий для заднего ракурса — графический адаптер; не допускать второго конкурирующего IK.
- В заднем ракурсе пользователь принял нейтральный сгиб ближнего правого колена; верх бедра и плечевые спрайты имеют локальные якоря. При рисовании сначала дальняя сторона, затем ближняя правая нога, затем **торс поверх её верхней части**, затем ближняя рука. Слои зависят от ракурса.
- Последняя подтверждённая серия встроенных проверок эталонного манекена — **24/24**, запуск `?qa=1`. Численные метрики не гарантируют, что новый персонаж выглядит правильно: обязательны Т-поза, вид в движении на телефоне и контроль швов/масштаба/перекрытий.
